# 小游戏设计标准

> **定位**：玩法、文字、交互、界面与验收的可执行标准。
> **适用**：`xechoz/<game>` 下的休闲 Web 小游戏（Phaser + `@mg/core`）。
> **不适用**：`mg-platform` 自身、`mini-games` 站点、Android/Flutter 原生项目。
> **关系**：流程与技术基线见 [`game-development.md`](game-development.md)；美术与动画见 [`art-standard.md`](art-standard.md)；硬规则以 `AGENTS.md` 为准。本文只补充设计质量，不复制硬规则。
> **优先级**：用户明确要求 > 既有设计系统（`@mg/core` 的 `theme`、`Button`、`Modal`）> 本文 > 文中示例数值。

| 阶段       | 读什么                                                    | 产出                         |
| ---------- | --------------------------------------------------------- | ---------------------------- |

| 调难度     | §3.10                                                     | 数据记录与单参数调整         |

**这份标准只做三件事**：给数字上限、列禁止项、定义验收动作。不写“要简洁”“要有质感”这类无法判定的形容词。

## 1. 四条第一原则

### 1.1 三秒可玩

冷启动到首次可操作 ≤ 3 秒、≤ 1 次点击。不做登录、不做开场 CG、不做说明页、不做多级菜单。

判定：从刷新页面开始计时，到玩家第一次有效输入为止。

### 1.2 零文字可懂

把界面文字全部关掉，游戏仍然能玩。

判定：临时把 i18n 文案替换成空字符串，跑一遍新手流程。任何一步卡住，都是设计问题，不是文案问题。

### 1.3 一屏一个决定

每个界面只有一个主操作。游戏内除了主操作，最多保留“暂停”。

判定：截图后遮住所有按钮，只留一个，玩家是否知道下一步点哪里。

### 1.4 反馈先于说明

想加解释文字时，先改成一次视觉、音频或触觉反馈。

判定：任何一条提示文案，问“能不能用一次高亮/箭头/慢动作替代”。能，就删文案。

## 2. 立项与范围

### 2.1 一页规格卡

开工前填完。填不出来不立项；填出来之后，卡上的内容就是范围上限。

| 字段       | 要求                                     |
| ---------- | ---------------------------------------- |
| `id`       | kebab-case，稳定不复用                   |
| 一句话描述 | ≤ 20 字，说清“玩家在干什么”              |
| 核心动词   | 只能 1 个（点 / 切 / 拖 / 叠 / 接 / 闪） |
| 目标       | 1 个，可量化                             |
| 失败条件   | 1 个                                     |
| 模式       | `endless` 或 `level`，二选一             |
| 参考游戏   | 必须写 1 个真实存在的游戏                |
| 差异点     | 1 句话，必须具体                         |
| 目标玩家   | 1 类人                                   |
| 单局时长   | 30–90 秒                                 |
| “啊哈”时刻 | 玩家第几秒会“哦——原来是这样”             |
| 分数维度   | 1 个                                     |
| 可调参数   | ≤ 10 个，全部进 `logic/config.ts`        |

两条附加规则：
- **必须有参考游戏。** 没有参考的立项一律不通过，否则 AI 会漂移成“什么都有一点”的通用玩法。
- **不允许“融合 A 和 B”作为立项理由。** 融合是结果，不是起点。

### 2.2 模式二选一

| 玩法特征                     | 模式                                         |
| ---------------------------- | -------------------------------------------- |
| 反应、躲避、切割、堆叠、节奏 | `endless` 无限模式                           |
| 解谜、机关、顺序、路径规划   | `level` 关卡制                               |
| 两者都行                     | **先做 `endless`**（片段库成本低于关卡编排） |

**禁止一个游戏同时做两套模式。** 同一批产品里可以两种都有，但单个游戏只能选一种；否则内容量、验收量和 AI 的发挥空间都会翻倍。

### 2.3 范围硬上限

| 项                                         | 上限               |
| ------------------------------------------ | ------------------ |
| 核心动词                                   | 1                  |
| 主动作（按钮 / 手势）                      | ≤ 2                |
| 失败条件                                   | 1                  |
| 分数维度                                   | 1                  |
| 局内机制（连击 / 道具 / 技能）             | ≤ 2                |
| 元系统（货币 / 升级 / 任务 / 体力 / 签到） | **0**              |
| 关卡机制种类                               | ≤ 5                |
| 单局决策间隔                               | 1–3 秒             |
| 首次可玩                                   | ≤ 3 秒、≤ 1 次点击 |
| 新手教程页                                 | **0**              |

判定方法：**删掉任何一个系统，游戏还能玩吗？能，就删。**

### 2.4 Non-goals

这一节比“做什么”更重要，直接列给 AI：
- 不做剧情、对话、CG、角色设定
- 不做货币、商店、升级、装备
- 不做体力、冷却、等待
- 不做多人、好友、排行榜（首版）
- 不做账号、云存档、跨端同步
- 不做超过 4 个设置项
- 不做新手教程页
- 不做“融合玩法”
- 不做需要读文字才能理解的机制
- 不做与核心动词无关的收集、成就、每日任务

## 3. 玩法标准

### 3.1 核心循环与节奏

| 指标       | 标准                                   |
| ---------- | -------------------------------------- |
| 输入到反馈 | ≤ 100ms                                |
| 输入缓冲   | 100–150ms（早按不算丢）                |
| 无反馈空窗 | 任何连续 3 秒必须有可见反馈            |
| 强度峰值   | 每 10–15 秒一次                        |
| 单局高潮   | 至少 1 次“差点失败 / 惊险通过”         |
| 局间空档   | 失败到重开 ≤ 2 秒                      |
| 等待型玩法 | **禁止**（无冷却、无读条、无“等体力”） |

核心循环必须闭合成一个圈：

```
操作 → 即时反馈 → 状态变化 → 下一步决策
```

任何一步超过 200ms，手感就散了。

### 3.2 无限模式：难度曲线

无限模式的难度是一条连续函数，不是台阶。要求是：**难度可感知、可预期、可归因。**

| 时间段     | 难度     | 规则                              |
| ---------- | -------- | --------------------------------- |
| 0–15 秒    | 0.2      | 教学期，只出现 1 种威胁，保证不死 |
| 15–60 秒   | 线性爬坡 | 每 10 秒升 1 档，每档 ≤ 8%        |
| 60 秒–3 分 | 减速爬坡 | 每 20 秒升 1 档，每档 ≤ 5%        |
| 3 分以后   | **封顶** | 难度不再上升，只比分数            |

封顶的理由：不封顶的结局是“迟早死”，玩家会觉得是时间问题，不是技术问题；封顶之后，高手的驱动力从“活得久”转成“打得分高”，重复游玩才有意义。

节奏要求：

| 指标             | 标准                               |
| ---------------- | ---------------------------------- |
| 强度峰值         | 每 20–30 秒一次                    |
| 喘息窗口         | 每个峰值后 2–3 秒低威胁            |
| 同屏威胁上限     | 按屏幕尺寸定，且不随难度无限增长   |
| 新威胁登场提前量 | ≥ 600ms                            |
| 威胁生成位置     | 禁止落在玩家安全区内               |
| 矛盾输入         | 禁止同时出现两个要求相反操作的威胁 |

目标数值：

| 指标              | 目标     |
| ----------------- | -------- |
| 新手首次死亡      | 30–60 秒 |
| 全体中位局时长    | 45–75 秒 |
| 前 10% 玩家局时长 | 2–3 分钟 |
| 单局上限          | ≤ 5 分钟 |

三条禁止：
1. **禁止隐藏 DDA。** 唯一允许的是“新手保护”：前 30 秒内连续死亡时，只允许单向放缓一次，幅度 ≤ 20%。
2. **禁止只靠加速。** 难度上升必须来自组合变化，不是所有东西一起变快。
3. **禁止不可解状态。** 生成器必须校验：至少存在一条合法操作序列。

### 3.3 无限模式：随机与公平

| 规则         | 要求                                         |
| ------------ | -------------------------------------------- |
| 随机的作用域 | 只决定“出现什么、什么顺序”，不决定“能不能过” |
| 同质连发     | 同一威胁不得连续出现 3 次                    |
| 保底         | 连续 2 个高压片段后，强制插入 1 个简单片段   |
| 难度分档     | 每个片段有明确难度标签，生成时按当前档位抽   |
| 种子         | 必须可复现，支持回放与复现 bug               |
| 死亡归因     | 每次死亡只能有一个主因                       |

验收时统计：**同一死因连续出现 3 次的概率必须为 0**（被保底规则强制排除）。

### 3.4 关卡制：难度曲线

| 项         | 标准                                 |
| ---------- | ------------------------------------ |
| MVP 关卡数 | 15–24 关                             |
| 单关时长   | 15–45 秒（教学关 10–20 秒）          |
| 总内容时长 | ≥ 3 分钟，目标 5–8 分钟              |
| 难度层级   | teaching / normal / challenge / boss |
| 挑战关节奏 | 每 5 关 1 个                         |
| 关卡选择   | 线性推进，不做世界地图               |

难度形状必须是**锯齿**，不能是台阶：

```
易 → 易 → 中 → 易 → 中 → 难 → 易 → 中 → 难 → Boss
```

规则：**每上一个难度台阶，后面必须跟 1 个回落的关卡。** 连续两关都是高难度，就会流失。

首次通过率目标：

| 关卡类型 | 首次通过率 |
| -------- | ---------- |
| 教学关   | 100%       |
| 普通关   | 60–80%     |
| 挑战关   | 30–50%     |
| Boss 关  | 20–40%     |

中位玩家在任一关的尝试次数 **> 3 次**，视为难度断崖，必须重做。

### 3.5 关卡制：教学节奏

| 位置       | 做法                                    |
| ---------- | --------------------------------------- |
| 第 1 关    | 只用 1 个动作，目标可见，几乎不可能失败 |
| 第 2–3 关  | 引入第 2 个元素，让玩家自己发现组合     |
| 第 4 关起  | 允许第一次失败                          |
| 新机制登场 | 慢动作 + 高亮 + 箭头，总时长 ≤ 2 秒     |
| 提示       | 失败 2 次后出现，≤ 6 字，2 秒消失       |
| 说明页     | **禁止**                                |

教学关的验收标准只有一条：**把文字全关掉，陌生人能自己通过。**

### 3.6 失败与公平（共用）

| 规则         | 要求                                |
| ------------ | ----------------------------------- |
| 可归因       | 玩家必须能说出“我因为 X 死的”       |
| 死因展示     | 定格 / 高亮 ≤ 0.5 秒，明确指出原因  |
| 判定宽容     | 判定框放大 10–20%，或容错 ≥ 3 帧    |
| 随机性       | 只允许影响呈现，不允许决定胜负      |
| 必须随机时   | 加保底：连续 N 次不利后必出有利     |
| 不可见陷阱   | **禁止**                            |
| 确认弹窗     | **禁止**（失败不需要“确定”）        |
| 差一点失败率 | 60–70% 的失败应发生在“差一点”范围内 |

最后一条是“再来一局”的真正驱动力：**玩家不是因为好玩而重开，是因为不甘心。** 如果失败总是差很远，他会直接退出。

### 3.7 数值管理

| 规则     | 要求                                                  |
| -------- | ----------------------------------------------------- |
| 数值位置 | 全部集中在 `src/logic/config.ts` 或 `logic/levels.ts` |
| 可调参数 | 每个游戏 ≤ 10 个                                      |
| 命名     | 语义化：`playerSpeed`、`spawnInterval`、`maxGap`      |
| 默认值   | 必须“开箱能玩”，不调参也能跑                          |
| 改动记录 | 每次调参写进 `CHANGELOG.md`（改了什么、为什么）       |
| 随机种子 | 必须可复现，便于定位和回放                            |

**禁止在场景、渲染、动画代码里写魔法数字。** 难度、速度、AI 决策时间只能来自配置。

### 3.8 内容

#### 3.8.1 无限模式：片段库

| 项         | 标准                                        |
| ---------- | ------------------------------------------- |
| 片段总数   | ≥ 20 个                                     |
| 难度分档   | 4 档，每档 ≥ 5 个                           |
| 单片段时长 | 3–10 秒                                     |
| 单片段新意 | 只包含 1 个新想法                           |
| 素材复用   | 每个片段不新增美术资产                      |
| 组合规则   | 第 3 档起允许两个片段拼接                   |
| 新鲜感     | 前 3 局内，每 20–30 秒出现 1 个没见过的片段 |

#### 3.8.2 关卡制：关卡内容

| 规则           | 要求                                               |
| -------------- | -------------------------------------------------- |
| 关卡格式       | 数据描述（TS 常量或 JSON），禁止把关卡写进场景代码 |
| 地块词汇量     | 每个游戏 ≤ 8 种                                    |
| 复用原则       | 新关卡 = 新组合，不是新素材                        |
| 每关标志性瞬间 | 至少 1 个                                          |
| 通关后         | 自动进入下一关，或 1 次点击                        |
| 新机制间隔     | ≥ 3 关                                             |
| 单关新增元素   | ≤ 1                                                |

数据化是硬要求：**改关卡不能改代码，不能重新构建。**

### 3.9 从想法到内容：拆解规范

前提：这套规范是给“AI 生成 + 人工验收”用的，字段必须少。**任何超过 10 个字段的模板，最后都会没人填。**

#### 3.9.1 五步链路（顺序不可换）

```
想法 → 机制原语 → 组合规则 → 片段 / 关卡 → 难度参数
```

#### 3.9.2 机制原语（primitive）

**定义：一个不可再拆的规则单元。** 它不知道自己在哪一关，也不知道自己属于哪个模式。

| 字段       | 说明                                     |
| ---------- | ---------------------------------------- |
| `id`       | `prim_` 前缀，稳定不复用                 |
| `trigger`  | 什么条件下触发（输入、时间、碰撞、状态） |
| `effect`   | 发生了什么状态变化                       |
| `feedback` | 玩家感知到什么（动画 / 音效 / 震动）     |
| `params`   | 可调数值，≤ 3 个                         |
| `fails`    | 是否可能导致失败                         |

三条约束：
1. **可单独测试**：能在一个空场景里跑起来。
2. **可组合**：不依赖特定关卡或其他原语。
3. **不含内容信息**：原语里不许出现“第 3 关”“Boss”这类词。

原语数量控制在 **6–10 个**。超过 12 个，说明玩法本身太复杂，回去砍。

#### 3.9.3 组合规则

不是所有原语都能放在一起。开工前定一张矩阵：

|          | `prim_a` | `prim_b` | `prim_c` |
| -------- | -------- | -------- | -------- |
| `prim_a` | —        | 可       | 禁       |
| `prim_b` | 可       | —        | 需条件   |
| `prim_c` | 禁       | 需条件   | —        |

三种关系：
- **可**：任意组合
- **需条件**：满足前置状态才能共存
- **禁**：互斥（例：同时要求“按住”和“快速点击”）

另外两条上限：
- 同屏同时生效的原语 **≤ 4 个**
- 单一片段内原语 **≤ 5 个**

#### 3.9.4 片段写法（无限模式）

| 字段          | 说明                     |
| ------------- | ------------------------ |
| `id`          | `pat_` 前缀              |
| `tier`        | 难度档 1–4               |
| `durationSec` | 3–10 秒                  |
| `uses`        | 用到的原语 id            |
| `solution`    | **预期解法，必须写出来** |
| `failDemo`    | 玩家会怎么死             |
| `linkable`    | 能否和其他片段拼接       |
| `requires`    | 前置片段                 |

两条硬规则：
1. **一个片段只能有一个新想法。** 有两个就拆成两个片段。
2. **`solution` 和 `failDemo` 写不出来，这个片段就不成立。** 说明它没有挑战，或者你自己也没想清楚。

#### 3.9.5 关卡写法（关卡制）

| 字段        | 说明                                 |
| ----------- | ------------------------------------ |
| `id`        | `lvl_` 前缀                          |
| `teaches`   | 本关引入的原语，没有就留空           |
| `uses`      | 用到的原语 id                        |
| `goal`      | 通关条件，可量化                     |
| `parSec`    | 预期通关秒数                         |
| `tier`      | teaching / normal / challenge / boss |
| `signature` | 本关的标志性瞬间，一句话             |
| `hint`      | ≤ 6 字，失败 2 次后才显示            |

三条硬规则：
1. **`teaches` 非空的关卡，`tier` 必须是 `teaching`，且首次通过率 100%。**
2. **`signature` 写不出来的关卡，删掉。** 它只是一个流程步骤，不是内容。
3. **关卡只能使用 `uses` 里列出的原语。** 超纲即 bug。

#### 3.9.6 难度参数

全游戏**只有一个全局难度旋钮**，其余都是局部参数。

| 类型                  | 数量     | 示例                       |
| --------------------- | -------- | -------------------------- |
| 全局旋钮              | 1        | 速度 / 生成间隔 / 时间压力 |
| 原语局部参数          | 每个 ≤ 3 | 重力、判定宽度、冷却       |
| 片段 / 关卡难度分 `D` | 1–5      | 由 tier 与 par 共同决定    |

难度分的使用方式：
- **无限模式**：生成器按当前 `D` 只抽 `tier ≤ ceil(D)` 的片段。
- **关卡制**：`D` 序列必须满足两条——单步涨幅 ≤ 1.0；任意连续 3 关中至少有 1 关回落。

这样“锯齿形难度”就从一句形容词变成了可以脚本校验的规则。

#### 3.9.7 内容与代码解耦

> **新增 10 个片段或关卡，代码 diff 必须为 0。**

如果加一关需要改代码，说明原语集不完整。正确做法是回到 3.9.2 补原语，而不是在关卡里写特判。

这条规则同时解决三个问题：
- AI 不会在关卡逻辑里塞魔法数字
- 内容可以热改，不用重新构建
- 一批游戏的关卡可以互相移植

#### 3.9.8 生产速率与单体验收

| 单元           | 目标耗时   | 验收                               |
| -------------- | ---------- | ---------------------------------- |
| 一个原语       | 1–2 小时   | 空场景可单独跑通                   |
| 一个片段       | 20–30 分钟 | `solution` 可复现，`failDemo` 成立 |
| 一个关卡       | 15–20 分钟 | 设计师连续通过 3 次                |
| 一批 20 个片段 | 1 天       | 覆盖 4 个难度档                    |

单体验收清单（每条都是二值）：
- [ ] `id` 唯一，前缀正确
- [ ] 只用一个新想法
- [ ] `solution` 可复现
- [ ] `failDemo` 成立
- [ ] 没有新增代码
- [ ] 难度分与实测一致（偏差 ≤ 0.5）

### 3.10 数据埋点与调参闭环

上面所有难度标准都依赖数据验证。没有数据，§3.2 和 §3.9.6 就只是纸面规则。

#### 3.10.1 约束

- **不上传、不引第三方统计。** 运行时零外部请求是硬规则。
- 只在本地记录最近 50 局，写进存档或内存。
- `?debug=1` 打开 `DebugOverlay`，支持导出 JSON 到剪贴板。
- 事件名固定，不超过 8 个；每个事件字段 ≤ 8 个。

#### 3.10.2 事件

| 事件                            | 字段                                                        |
| ------------------------------- | ----------------------------------------------------------- |
| `run_start`                     | `gameId`、`mode`、`seed`、`levelId?`                        |
| `run_end`                       | `durationMs`、`score`、`deathCause`、`levelId?`、`attempt?` |
| `level_start`                   | `levelId`、`attempt`                                        |
| `level_end`                     | `levelId`、`attempt`、`durationMs`、`deaths`                |
| `hint_shown`                    | `levelId?`、`trigger`                                       |
| `retry`                         | `from`、`delayMs`                                           |
| `session_start` / `session_end` | `at`                                                        |

#### 3.10.3 调参只看三个指标

| 指标              | 用途                           |
| ----------------- | ------------------------------ |
| 中位局时长        | 判断节奏是太快还是太拖         |
| 死因分布          | 判断公平性与内容问题           |
| 重开率 / 重开延迟 | 判断失败成本与“再来一局”驱动力 |

#### 3.10.4 调参流程

1. 跑 20 局（自己玩，或用纯逻辑模拟）。
2. 看分布，不看单局。
3. **一次只改一个参数。**
4. 再跑 20 局。
5. 把 before / after 写进 `CHANGELOG.md`。

#### 3.10.5 判定规则

**无限模式：**
- 中位局时长 < 30 秒 → 降初始难度
- 中位局时长 > 120 秒 → 加快爬坡或提前封顶
- 单一死因 > 50% → 检查该片段是否不公平
- 重开率 < 50% → 失败成本太高，或“差一点”比例不够

**关卡制：**
- 单关通过率低于目标区间 → 降难度或补教学
- 单关中位尝试 > 3 次 → 难度断崖
- 某一关退出率 > 30% → 重做该关

#### 3.10.6 自动化验收

因为 `src/logic` 是纯函数，可以直接在 Vitest 里跑模拟：

```ts
// 伪代码
it('1000 runs never reach an unwinnable state', () => {
  for (let seed = 0; seed < 1000; seed++) {
    const result = simulate(seed)
    expect(result.unwinnable).toBe(false)
    expect(result.deathCause).toBeTruthy()
  }
})
```

要求：
- 无限模式至少 1000 局模拟，0 次不可解状态。
- 局时长中位数落在配置目标区间。
- 死亡主因 100% 非空。

### 4.1 文字预算

| 位置                       | 上限                                    |
| -------------------------- | --------------------------------------- |
| 游戏内常驻文字             | ≤ 4 个元素，合计 ≤ 16 字                |
| 单次提示（toast / hint）   | ≤ 6 字，同屏 1 条，2 秒自动消失         |
| 按钮                       | ≤ 4 字，首选 2 字（继续 / 重来 / 开始） |

### 4.3 交互预算

| 项                        | 上限                                 |
| ------------------------- | ------------------------------------ |
| 主菜单可点元素            | ≤ 3                                  |

| 规则            | 要求                                  |
| --------------- | ------------------------------------- |
| 输入队列 / 缓冲 | 必须有，100–150ms                     |
| 非法输入        | 拒绝，不吞掉下一次合法输入            |
| 失焦 / 切标签页 | 停表；恢复给 3-2-1 倒计时             |
| 输入反馈        | 每个输入都有视觉或音频反馈            |
| 判定宽容        | 判定框放大 10–20%                     |

| 状态       | 要求                               |
| ---------- | ---------------------------------- |

## 5. 界面标准

### 5.1 十二条

1. **层级靠减淡。** 主角不突出时，先削弱竞争者，不要给主角加戏。
2. **一切取值来自系统。** 字号、间距、颜色、圆角、阴影必须来自 `theme` 或本文的尺度，不在场景里手调。
3. **组间距 ≥ 组内 × 2。** 横竖都算。这一条修掉大部分“说不清哪里不对”。
4. **一屏一个主操作。** 实心强按钮 ≤ 2。
5. **正文行宽。** 中文 20–35 字/行，西文 45–75 字符。
6. **文字色 ≤ 3 档。** 彩色底上不用灰字，用同色相降饱和。
7. **不只靠颜色。** 每个颜色编码必须有图标、形状或位置的第二线索。
8. **触控目标 ≥ 44 CSS px。** 在 720 设计空间下按 §5.9 换算。
9. **阴影表达层级，不表达重要性。** 静态元素不用高层级阴影。
10. **空状态是功能的一部分。** 不是事后补的。
11. **HUD 元素必须改变玩家决策。** 不能改变决策的，删。
12. **动效尊重“减少动效”。** 系统开启后，去掉装饰性动画，保留必要反馈。

### 5.2 共享外壳

固定五个界面：**Menu / Play / Pause / Result / Settings**。
- 每个游戏只提供：Play 场景、Result 数据、一个图标、主题色。
- 游戏内不放设置入口，设置只在暂停里。
- 暂停与结算复用 `Modal`，不自己画弹窗。
- 按钮复用 `Button`，变体只用 `primary / soft / ghost / danger`。

### 5.3 HUD

| 规则     | 要求                                |
| -------- | ----------------------------------- |
| 常驻元素 | ≤ 4 个                              |
| 位置     | 左上分数、右上暂停、底部主操作      |
| 分数     | 大号、等宽数字或 `displayTextStyle` |
| 暂停     | 固定右上角，触控目标 ≥ 44 CSS px    |
| 进度     | 用图形，不用文字百分比              |
| 提示     | 同屏 ≤ 1 条，非阻塞                 |
| 遮挡     | 不覆盖主操作区与安全区              |

### 5.4 结算页

固定结构，禁止自由发挥：

```
结果（大）
最佳 / 新纪录（小）
[主按钮]  再来一局
[次按钮]  回菜单
[可选]    奖励入口
```

| 规则   | 要求                                     |
| ------ | ---------------------------------------- |
| 行数   | ≤ 3 行                                   |
| 主按钮 | 1 个，实心                               |
| 次按钮 | ≤ 1 个，soft 或 ghost                    |
| 动画   | ≤ 700ms 后必须可操作                     |
| 新纪录 | 用颜色 + 图标 + 文案三重提示             |
| 差一点 | 显示具体差距（差 20 分），不写“继续努力” |

### 5.5 暂停与设置

| 规则     | 要求                           |
| -------- | ------------------------------ |
| 暂停     | 停表、静音、锁输入             |
| 恢复     | 3-2-1 倒计时                   |
| 设置项   | ≤ 4 个                         |
| 设置入口 | 只在暂停 / 菜单                |
| 设置保存 | 走 `mg:settings:v1` 或游戏存档 |
| 关闭设置 | 1 次点击返回                   |

### 5.6 间距与布局

基准单位：**设计空间短边 720**。1 设计单位 = 视口短边 CSS 像素 / 720。

间距阶：

```
4  8  12  16  24  32  48  64  96  128
```

规则：
- 单屏出现的档位 ≤ 5 种。
- 组间距 ≥ 组内 × 2。
- 不够用往上取一档，不插中间值。
- 安全区用 `readViewport(scene).insets`，不写死。

### 5.7 字号与文字色

字号阶：

```
16  20  24  28  32  40  48  64  80
```

| 用途        | 字号（设计单位） | 360px 短边屏约 |
| ----------- | ---------------- | -------------- |
| 辅助 / 标签 | 20–24            | 10–12 CSS px   |
| 正文        | 28–32            | 14–16 CSS px   |
| 按钮        | 28–32            | 14–16 CSS px   |
| HUD 数值    | 40–64            | 20–32 CSS px   |
| 标题        | 48–80            | 24–40 CSS px   |

规则：
- 档位 ≤ 8；不跨档取中间值。
- 中文用系统字体栈（`theme.font`），不打包 CJK 字体。
- 文字色 ≤ 3 档：`theme.text` / `theme.textMuted` / 同灰阶手选一档。
- 正文对比度 ≥ 4.5:1，大字 ≥ 3:1。
- 大字号标题用 `displayTextStyle`，正文用 `textStyle`。

### 5.8 颜色

| 规则         | 要求                                                        |
| ------------ | ----------------------------------------------------------- |
| 色板来源     | `theme`，游戏通过 `GameDefinition.theme` 覆盖               |
| 主色来源     | 必须是 `theme.accent`，或 `GameDefinition.theme` 的显式覆盖 |
| AI 默认色    | **禁止** Claude 橙及同色相区间（见 §5.8.1）                 |
| 硬编码色值   | 场景 / UI / 动画里 **0 处**                                 |
| 单屏色相     | ≤ 3                                                         |
| 语义色       | 成功 / 警告 / 危险 / 信息，各有明确用途                     |
| 大面积彩色块 | ≤ 屏面 1/3                                                  |
| 强调色面积   | ≤ 10%                                                       |
| 渐变色相差   | ≤ 30°                                                       |
| 灰阶         | 带温度，不用纯灰                                            |
| 运行时调色   | 禁止在使用点 `lighten/darken`，新增档位整族补齐             |

### 5.8.1 主色必须来自项目

AI 生成界面时有一个稳定漂移：不管项目主题是什么，一律上 Claude 橙（Anthropic 的品牌色）。结果是所有游戏看起来像同一个产品，并且和项目既有主题打架。

规则：
1. **默认主题优先。** 新游戏从 `defaultTheme` 开始；没有品牌理由不覆盖。当前默认主色是 `accent` 青蓝（`#38bdf8`），辅助强调 `accentAlt` 绿（`#35c77e`），`accentWarm` 浅黄（`#fff1b8`）只做点缀。
2. **主色只有一个来源。** 只能写在 `src/main.ts` 的 `GameDefinition.theme` 里；组件里只能引用 `theme.*`。
3. **禁止 Claude 橙作为默认强调色。** 黑名单：
   - `#D97757`
   - `#CC785C`
   - `#C15F3C`
   - 以及 HSL 落在 **H 10–30°、S 40–70%、L 45–65%** 的同类色
4. **游戏主题确实是橙色时**，必须在立项卡 `Theme override` 写明理由，并在 `GameDefinition.theme` 显式定义；组件仍然只能引用 token。
5. **语义色不受主色限制**，但危险色不得使用 Claude 橙，避免和主色混淆。

检查方式：

```bash
# 场景与 UI 层不允许出现十六进制色值
rg -n '#[0-9a-fA-F]{6}|0x[0-9a-fA-F]{6}' src/scenes src/ui

# 全仓库不允许出现 Claude 橙
rg -n '#D97757|#CC785C|#C15F3C' src
```

两条命令都必须无输出。**主色是项目的身份，不是模型的默认值。**

### 5.9 触控目标

换算公式：

```
设计单位 = 44 × 720 / 视口短边 CSS 像素
```

| 视口短边 | 44 CSS px 对应 |
| -------- | -------------- |
| 360 px   | 88 设计单位    |
| 390 px   | 81 设计单位    |
| 430 px   | 74 设计单位    |

规则：
- 触控目标 ≥ 44 CSS px，主操作建议 ≥ 48 CSS px。
- 视觉尺寸可以小于触控区，用 `Button.minHitSize` 扩大热区。
- 相邻可点元素之间留 ≥ 8 CSS px 间距。
- 现有游戏中 `minHitSize: 44–48` 在手机上低于 44 CSS px，新游戏按本节换算，存量游戏下次大改时收敛。

### 5.10 横竖屏与安全区

| 规则       | 要求                                                   |
| ---------- | ------------------------------------------------------ |
| 横竖屏     | 都必须可玩，不注入旋转遮罩或强制旋转提示               |
| 移动端横屏 | 可尝试锁定，失败/不支持/退出全屏时回退                 |
| 安全区     | 刘海、手势条、系统栏；用 `insets`                      |
| 布局       | 用 `readViewport`，不用 `scene.scale.width` 当设计宽度 |
| 最小宽度   | 320 CSS px 下核心功能完整可用                          |
| 文本膨胀   | 英文/德文比中文长 30–40%，按钮按最坏情况留宽           |

## 6. 性能预算

“元素多了就卡”一半是引擎问题，一半是内容没有预算。

### 6.1 指标

| 指标          | 健康值                    | 超标说明                  |
| ------------- | ------------------------- | ------------------------- |
| draw call     | ≤ 30                      | 批处理被打断              |
| 单帧 JS       | ≤ 8ms                     | 逻辑 / 对象更新过重       |
| 同屏精灵      | ≤ 300（同 atlas）         | 纹理切换才是问题          |
| 同屏 tween    | ≤ 100                     | 超过就合并                |
| 纹理 / 场景   | ≤ 3                       | 每换一张纹理断一批        |
| 同屏粒子      | ≤ 40                      | 见 `art-standard.md`      |
| 每帧 new 对象 | 0                         | 用对象池                  |
| DPR           | ≤ 3（`MAX_RENDER_SCALE`） | 已由 `renderMetrics` 限制 |

### 6.2 Phaser 规则

| 症状                | 真实原因                             | 修法                                               |
| ------------------- | ------------------------------------ | -------------------------------------------------- |
| 分数/计时一出现就卡 | `setText` 每帧重绘 canvas 再上传纹理 | `BitmapText`，或预渲染数字图集，只在数值变化时更新 |
| 精灵越多越卡        | 每个精灵独立纹理                     | 打进一个 atlas                                     |
| 加特效就掉帧        | blend mode、mask、postFX 打断批次    | 游戏内禁用 mask / postFX，用贴图伪造               |
| 加图形就卡          | `Graphics` 每帧重新三角化            | 画一次 `generateTexture()` 缓存                    |
| 动画多了卡          | tween 数量爆炸 + `onUpdate` 闭包     | 合并 timeline，去掉 `onUpdate`                     |
| 越玩越卡            | 每帧 new 对象、未回收粒子/子弹       | 对象池，`update` 里零分配                          |
| 物理卡              | 用了 Matter.js                       | 换 Arcade；Matter 超过几百个 body 很贵             |
| 低端机特别卡        | 3x DPR 渲染 = 9 倍像素               | 已由 `renderMetrics` 限制到 3，必要时降到 2        |

两个隐蔽项：
- `setVisible(false)` 的对象仍然参与更新，要用 `setActive(false)`。
- 嵌套 Container 的每帧矩阵计算会叠乘。

### 6.3 诊断

1. 打开 `DebugOverlay`，看 `game.loop.actualFps`。
2. 用 Spector.js 抓一帧，看 draw call 数。> 100 就是批处理问题。
3. 二分法关元素：粒子 → 文字 → tween → 物理。哪一步恢复，问题就在哪。
4. Chrome Performance 录 5 秒，看主线程是 JS 满还是 GPU 满。

**没测出具体数字之前，不要换引擎。**

## 8. 反模式

| 反模式               | 后果                   |
| -------------------- | ---------------------- |
| 用文字解释规则       | 玩家不读，且显得廉价   |
| 一屏多个主按钮       | 没有主次，点击率下降   |
| 加货币 / 升级 / 任务 | 范围爆炸，休闲变中核   |
| 失败弹确认框         | 打断节奏，重开成本翻倍 |
| 隐藏 DDA             | 玩家感知为作弊         |
| 只靠加速提升难度     | 难度断崖，体验单调     |
| 用代码写关卡         | 内容生产被工程阻塞     |
| 用 Claude 橙当主色   | 所有项目长一个样       |
| 魔法数字散落         | 难度不可调，不可复现   |
| 每帧 `setText`       | 帧率断崖               |
| 每个精灵独立纹理     | draw call 爆炸         |
| 一个片段塞两个新想法 | 难度不可归因           |
| 不写预期解法         | 自己都过不去           |
| 结算页自由发挥       | 一批游戏风格不一致     |

## 附录 D：文案预算测试示例

```ts
import { describe, expect, it } from 'vitest'
import { zh } from './i18n'

const BUDGET: Record<string, number> = {
  'menu.play': 4,
  'hud.pause': 2,
  'result.retry': 4,
  'result.menu': 4,
  'hint.default': 6,
}

describe('i18n text budget', () => {
  for (const [key, max] of Object.entries(BUDGET)) {
    it(`${key} <= ${max} chars`, () => {
      const value = key.split('.').reduce<unknown>((node, part) => {
        if (typeof node !== 'object' || node === null) return undefined
        return (node as Record<string, unknown>)[part]
      }, zh)
      expect(typeof value).toBe('string')
      expect((value as string).length).toBeLessThanOrEqual(max)
    })
  }
})
```
